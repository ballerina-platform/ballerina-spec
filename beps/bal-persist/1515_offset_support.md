# Offset support for `bal persist` SQL clients

- Author: @niveathika
- Reviewers:
- Created: 2026-10-25
- Updated: 2026-10-26
- Issue: [#1515](https://github.com/ballerina-platform/ballerina-spec/issues/1515)
- Status: Submitted

## Summary

`persist.sql` clients run the `where`, `order by`, `limit` and `group by` clauses of a query
expression in the database, but they cannot skip rows. This proposal adds an `offsetClause`
argument to the `get` resource of generated SQL clients and allows it inside a query
expression, so a page of results is read in one SQL query.

Please add any comments to issue [#1515](https://github.com/ballerina-platform/ballerina-spec/issues/1515).

## Goals

- Skip rows in the database when reading entities through a `persist.sql` client.
- Keep the meaning of a query the same whether its clauses run in the database or in memory.
- Support MySQL, PostgreSQL, H2 and MSSQL.
- Keep clients generated by earlier tool versions working.

## Non-Goals

- An `offset` clause in Ballerina query expressions. That is a language change; see
  [Future Work](#future-work).
- Offset for the in-memory, Google Sheets and Redis datastores.
- Cursor paging and total counts.

## Motivation

Paging is the most common reason to read part of a table: a list view shows rows 21 to 30, an
export reads a large table in batches. Today a `persist.sql` client can return the first `n`
rows but cannot skip any, so users either read every row and drop the ones they don't need, or
fall back to `queryNativeSQL` and lose the typed `targetType` projection and relation loading.

[ballerina-library#5846](https://github.com/ballerina-platform/ballerina-library/issues/5846)
asked for this and was closed because query expressions have no `offset` clause. The generated
client, however, already takes each clause as a `sql:ParameterizedQuery` argument. An offset
argument fits that shape and needs no language change.

## Design

### Current behaviour

This section records how clauses reach the database today, since no spec covers it.

A SQL datastore client generates a `get` resource per entity that takes each clause as a
parameterized query. The list form exists when the tool generates list return types.

```ballerina
isolated resource function get employees(EmployeeTargetType targetType = <>,
        sql:ParameterizedQuery whereClause = ``, sql:ParameterizedQuery orderByClause = ``,
        sql:ParameterizedQuery limitClause = ``, sql:ParameterizedQuery groupByClause = ``)
        returns stream<targetType, persist:Error?>;

isolated resource function get employees(EmployeeTargetType targetType = <>,
        sql:ParameterizedQuery whereClause = ``, sql:ParameterizedQuery orderByClause = ``,
        sql:ParameterizedQuery limitClause = ``) returns targetType[]|persist:Error;
```

The client builds `SELECT … FROM … [JOIN …] WHERE … GROUP BY … ORDER BY … LIMIT …`, leaving
out each clause whose argument is empty.

The `persist.sql` compiler plugin rewrites a query expression whose source is a `get` call on a
persist client. It moves the query's `where`, `order by`, `group by` and `limit` clauses into
the matching arguments, so they run in the database:

```ballerina
Employee[] employees = check from Employee e in db->/employees(targetType = Employee)
    where e.age > 30
    order by e.empNo
    limit 10
    select e;
```

A query is rewritten only when all of these hold. Otherwise the clauses run in memory, on every
row the client returns.

- The client is a variable declared with the generated client type. A field access such as
  `self.db` is not recognized
  ([ballerina-library#4943](https://github.com/ballerina-platform/ballerina-library/issues/4943)).
- The call passes only `targetType`. Passing a clause argument inside a query expression is the
  error `PERSIST_202`.
- The query has no `let` clause.
- The `where` clause uses only field access, literals, variables, function calls, comparison
  operators, `&&` and `||`.
- `limit` is an integer literal, a variable or a function call (`PERSIST_205` otherwise).

Outside a query expression, the arguments are passed to the database as written.

### The `offsetClause` argument

Both forms of the `get` resource gain one argument, after the existing ones:

```ballerina
isolated resource function get employees(EmployeeTargetType targetType = <>,
        sql:ParameterizedQuery whereClause = ``, sql:ParameterizedQuery orderByClause = ``,
        sql:ParameterizedQuery limitClause = ``, sql:ParameterizedQuery groupByClause = ``,
        sql:ParameterizedQuery offsetClause = ``) returns stream<targetType, persist:Error?>;

isolated resource function get employees(EmployeeTargetType targetType = <>,
        sql:ParameterizedQuery whereClause = ``, sql:ParameterizedQuery orderByClause = ``,
        sql:ParameterizedQuery limitClause = ``, sql:ParameterizedQuery offsetClause = ``)
        returns targetType[]|persist:Error;
```

**Value.** The argument holds one non-negative `int`, either as a literal (`` `20` ``) or as a
single interpolation (`` `${start}` ``), with only whitespace around it. Any other value, such
as a negative number, a string or SQL text, fails with a `persist:Error` before the query runs,
so the caller gets the same error on every database. An interpolated value is bound as a
parameter, as the values of `whereClause` are; every supported database accepts a parameter
for the offset and the limit.

**Meaning.** The database skips that many rows after `where`, `group by` and `order by`, and
before `limit`, as SQL `OFFSET` does. An empty argument skips nothing. Without an order, which
rows are skipped is up to the database, so a page is only stable with `order by` on a unique
key.

```ballerina
// SELECT ... WHERE age > ? ORDER BY empNo LIMIT 10 OFFSET 20
stream<Employee, persist:Error?> page = db->/employees(targetType = Employee,
        whereClause = `age > ${30}`, orderByClause = `empNo`, limitClause = `10`,
        offsetClause = `${20}`);
```

### In query expressions

`offsetClause` may be passed in a query expression's `get` call, together with `targetType`.
It is the one clause argument `PERSIST_202` allows. The compiler plugin keeps it when it
rewrites the call:

```ballerina
Employee[] page = check from Employee e in db->/employees(targetType = Employee,
        offsetClause = `${start}`)
    where e.age > 30
    order by e.empNo
    limit 10
    select e;
// SELECT ... WHERE age > ? ORDER BY empNo LIMIT 10 OFFSET <start>
```

The offset is applied in the database, so the query's other clauses must be too. If the query
has a `where`, `order by` or `group by` clause and is not rewritten, for any reason listed in
[Current behaviour](#current-behaviour), it is a compile error:

```
PERSIST_207: 'offsetClause' needs the query's 'where', 'order by' and 'group by' clauses to run
in the database, but this query runs them in memory
```

Without the error, those clauses would run on the rows left after the offset, and the query
would return a different page from the same query rewritten. A `limit` alone is not checked:
taking `n` rows after the offset gives the same rows in the database and in memory.

### Datastores

Each datastore gets the syntax it accepts:

| Datastore | `limit` and offset | Offset only | Limit only |
|---|---|---|---|
| MySQL | `LIMIT n OFFSET m` | `LIMIT 18446744073709551615 OFFSET m` | `LIMIT n` |
| PostgreSQL, H2 | `LIMIT n OFFSET m` | `OFFSET m` | `LIMIT n` |
| MSSQL | `ORDER BY … OFFSET m ROWS FETCH NEXT n ROWS ONLY` | `ORDER BY … OFFSET m ROWS` | `ORDER BY … OFFSET 0 ROWS FETCH NEXT n ROWS ONLY` |

MySQL does not accept `OFFSET` without `LIMIT`; the large limit is the form its manual gives
for "all remaining rows".

MSSQL has no `LIMIT`, so a limit alone is written as `OFFSET 0 ROWS FETCH NEXT n ROWS ONLY`.
`OFFSET … FETCH` needs an `ORDER BY`. Without `orderByClause`, the client adds
`ORDER BY (SELECT NULL)` in each MSSQL form, which keeps the database's order.

The datastore's syntax is a new field of `DataSourceSpecifics`, with a default so existing
values keep the current behaviour:

```ballerina
# The syntax a datastore uses to skip and limit rows.
public enum PaginationSyntax {
    # `LIMIT n OFFSET m`, where `OFFSET m` may stand alone
    LIMIT_OFFSET,
    # `LIMIT n OFFSET m`, where `OFFSET m` needs a `LIMIT`
    LIMIT_REQUIRED_WITH_OFFSET,
    # `ORDER BY … OFFSET m ROWS FETCH NEXT n ROWS ONLY`
    OFFSET_FETCH
}

public type DataSourceSpecifics record {|
    // existing fields
    PaginationSyntax paginationSyntax = LIMIT_OFFSET;
|};
```

`MYSQL_SPECIFICS` uses `LIMIT_REQUIRED_WITH_OFFSET`, `MSSQL_SPECIFICS` uses `OFFSET_FETCH`, and
`POSTGRESQL_SPECIFICS` and `H2_SPECIFICS` keep the default.

### Compatibility

- `SQLClient.runReadQuery` and `SQLClient.runReadQueryAsList` take `offsetClause` as a new last
  parameter with an empty default.
- Generated clients bind the `get` resources to the native `queryWithOffset` and
  `queryAsListWithOffset` functions, which take the extra argument. They are new names rather
  than overloads of `query` and `queryAsList`, because Java interop matches overloads by
  argument count and treats the leading `Environment` parameter as optional, so overloads one
  argument apart cannot be told apart. `query` and `queryAsList` stay, so a client generated
  before this change keeps compiling and running, without the offset argument. Regenerating
  adds it.
- `persist-tools` generates the argument and its doc line for every SQL datastore. Clients it
  generates need a `persist.sql` version that has the new functions.
- Queries that pass `offsetClause` are new, so `PERSIST_207` cannot break existing code.

## Alternatives

**An `offset` clause in query expressions.** This reads best and needs no argument, but it is a
language change. The argument works now, and maps onto the clause later; see
[Future Work](#future-work).

**An `int offset` argument.** Inside a query expression, `offset = start` reads more naturally
than `` offsetClause = `${start}` ``. The type would also be checked at compile time, so the
runtime check would not be needed. It was set aside for now to match the other clause arguments,
which are all `sql:ParameterizedQuery`, and the parameterized queries the compiler plugin writes
when it rewrites a query. When query expressions get an `offset` clause, users stop writing the
argument in queries, so its type matters less there.

**Keep `queryNativeSQL`.** It works today, but the user writes the whole query and loses
`targetType` projection and relation loading.

## Testing

For each of MySQL, PostgreSQL, H2 and MSSQL:

- Offset only, `limit` and offset, and offset with `where` and `order by`, through the stream
  and list forms.
- A query expression that passes `offsetClause` and is rewritten, checked against the same page
  read with all arguments passed directly.
- Invalid values: negative, a string, SQL text, more than one interpolation.
- MSSQL: offset without `order by`, with and without `limit`, and `limit` alone, with and
  without `order by`.
- A client generated without `offsetClause` still runs.

Compiler plugin:

- `offsetClause` in a query expression does not raise `PERSIST_202`, and is kept by the
  rewrite.
- `PERSIST_207` for a query with `offsetClause` and a `where` clause when the client is a field
  access, when the query has a `let` clause, and when the `where` clause is not supported.
- No error for a query with `offsetClause` and only `limit`.

## Risks and Assumptions

- Offset pages shift when rows before them are inserted or deleted, and a large offset makes
  the database read and discard every skipped row. Cursor paging avoids both; the
  documentation says so.
- On MSSQL, `ORDER BY (SELECT NULL)` keeps whatever order the database reads in, which can
  change between queries. A stable page needs an `order by` on a unique key, as on every other
  datastore.

## Dependencies

- `persist-tools` must be released after the `persist.sql` version with the new native functions.

## Future Work

- When query expressions get an `offset` clause, the compiler plugin rewrites it into
  `offsetClause` the way it rewrites `limit`. Passing `offsetClause` in a query expression then
  becomes an error again (`PERSIST_202`), and outside query expressions it stays.
- A total row count for paged results.
